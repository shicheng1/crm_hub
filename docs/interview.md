# 面试讲解稿

## 1. 项目一句话介绍

这是一个企业内部工单审批系统，支持动态审批流、多级审批、多审批人、驳回策略、实时通知、Redis 缓存、分布式锁、接口限流、RabbitMQ 异步消息、WebSocket 推送和 Docker Compose 部署。

## 2. 简历写法

```text
企业级工单审批系统 | Spring Boot + Vue3
- 设计并实现多级审批流引擎，支持多审批人、自动跳过、三种驳回策略和审批记录追踪。
- 使用 Redis 实现分布式锁、工单缓存、空值缓存、JWT 主动失效和 Lua 滑动窗口限流。
- 引入 RabbitMQ + WebSocket 实现审批结果异步通知和实时推送。
- 使用 MyBatis-Plus 分页与批量查询优化列表接口，减少 N+1 查询。
- 补齐 Docker Compose、Nginx、Actuator 健康检查、GitHub Actions、单元测试和生产配置分层。
```

## 3. 项目架构怎么讲

我这个项目采用前后端分离架构：前端是 Vue3 + Vite + Element Plus，后端是 Spring Boot 2.7 + MyBatis-Plus。数据存储用 MySQL，Redis 承担缓存、分布式锁、限流和 token 管理，RabbitMQ 做审批通知异步解耦，WebSocket 把审批结果实时推送给前端。部署上用 Docker Compose 编排 MySQL、Redis、RabbitMQ、后端和 Nginx 前端。

## 4. 核心亮点

### 4.1 审批流引擎

可以讲：

- 审批流由 `approval_flow` 和 `approval_flow_step` 配置。
- 一个步骤可以配置多个审批人，存在 `approval_step_approver` 表。
- 工单记录当前步骤 `current_step`。
- 审批通过后查找下一步骤。
- 如果后续步骤审批人和当前审批人相同，会自动跳过。
- 驳回支持 `RESTART`、`PREVIOUS`、`ORIGIN` 三种策略。

面试表达：

> 我没有把审批节点写死在代码里，而是抽成了审批流模板和审批步骤表。工单创建时绑定流程，审批时根据当前步骤找审批人和下一步骤。这样新增流程不需要改代码，只需要配置数据。

### 4.2 分布式锁

可以讲：

- 加锁使用 Redis `SET key value NX EX`。
- value 包含唯一标识，避免误删别人的锁。
- 解锁用 Lua 保证“判断 value + 删除 key”的原子性。
- 使用场景：创建工单防重复提交、审批工单防并发审批。

面试表达：

> 审批接口是典型的并发敏感接口，如果两个审批人同时操作同一个工单，可能出现重复审批或状态覆盖。我用 Redis 分布式锁按 orderId 加锁，保证同一时间只有一个审批流程能修改该工单状态。

### 4.3 缓存设计

可以讲：

- 工单详情走 Cache Aside。
- 查询先读 Redis，未命中读 MySQL 并写缓存。
- 修改审批状态后删除工单缓存。
- 工单不存在时缓存空值，防止缓存穿透。
- 看板统计缓存 5 分钟，审批后主动失效。

面试表达：

> 我选择 Cache Aside，是因为业务修改频率不高、读多写少。写操作后删除缓存，让下一次查询回源数据库并重建缓存。对不存在的工单 ID，我做了短 TTL 空值缓存，避免恶意请求打穿数据库。

### 4.4 限流

可以讲：

- 使用自定义 `@RateLimit` 注解。
- 拦截器识别注解参数。
- Redis + Lua 实现滑动窗口。
- 已登录按用户 ID 限流，未登录按 IP 限流。
- 登录接口和创建工单接口已接入。

面试表达：

> 限流没有写死在接口里，而是做成注解。这样接口只需要标注 key、窗口时间和最大请求数，拦截器统一处理，扩展比较方便。

### 4.5 RabbitMQ + WebSocket 通知

可以讲：

- 审批后构造 `ApprovalMessage`。
- RabbitMQ 负责异步通知处理。
- WebSocket 负责推送到用户个人频道。
- 前端订阅 `/topic/notifications/{userId}`。
- MQ 可关闭，关闭时可降级同步推送。

面试表达：

> 审批和通知是两个不同关注点，我用 MQ 解耦，避免通知逻辑阻塞主审批链路。同时用 WebSocket 做实时推送，让创建人不用刷新页面就能收到审批结果。

### 4.6 SQL 优化

可以讲：

- 列表分页用 MyBatis-Plus 分页。
- 批量查询创建人，避免逐条查用户。
- 审批流列表批量查步骤和审批人。
- 待办/已办通过 JOIN 查询减少多次查询。

面试表达：

> 项目里我重点处理了 N+1 查询问题，例如审批流列表不是每个流程单独查步骤和审批人，而是批量查出再按 flowId、stepId 分组组装。

### 4.7 生产部署

可以讲：

- 后端有 `application-prod.yml`。
- 敏感配置通过环境变量注入。
- Docker Compose 编排完整环境。
- 前端 Nginx 托管静态资源并代理 API/WebSocket。
- Actuator 提供健康检查。
- GitHub Actions 执行后端测试、前端构建和 Compose 校验。

## 5. 常见追问

### Q1：为什么 JWT 还要存 Redis？

JWT 本身无状态，服务端不能主动让 token 失效。把 token 存 Redis 后，登出时删除 Redis key，拦截器校验时同时校验 JWT 和 Redis 是否存在，就能实现主动注销。

### Q2：为什么不用数据库行锁？

行锁只能覆盖单库事务内的并发。如果后端部署多个实例，应用层还需要跨实例互斥。Redis 分布式锁可以在多实例场景下保证同一工单同一时间只被一个请求处理。

### Q3：缓存一致性怎么保证？

采用 Cache Aside：读时未命中再写缓存，写时先更新数据库再删除缓存。审批业务写频率不高，允许极短时间不一致。如果要更强一致，可以加延迟双删或通过 MQ 异步删除缓存。

### Q4：MQ 消息失败怎么办？

消费者使用手动 ACK，业务成功后确认。消费失败可以 nack 不重新入队，避免无限重试；生产环境可以配死信队列记录失败消息，再由补偿任务处理。

### Q5：审批流修改后历史工单怎么办？

当前版本工单绑定的是流程 ID，后续生产级升级会做流程版本化或流程快照。工单创建时保存当时的流程版本，避免流程修改影响历史工单。

### Q6：项目最大的改进空间是什么？

下一步是 RBAC 接口权限、审批流版本化、条件审批、会签、traceId 日志链路、Prometheus 指标和压测报告。
